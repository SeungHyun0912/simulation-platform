## 1. 운영 원칙
- API, UI, 통합 검증 세션 모두 작업 전 최신 파일과 Git 상태를 확인한다.
- 이 문서는 작업·인계의 기준이며 API 계약이나 도메인 명세를 대체하지 않는다.
- 각 작업의 책임자는 한 역할로 지정한다. 여러 영역이면 하위 작업으로 나눈다.
- 한 파일을 여러 세션이 동시에 수정하지 않는다. 편집은 순차 예약하고 저장 직전 diff를 확인한다.
- 별도 브랜치에서는 문서 변경도 병합해야 다른 세션에서 보인다. 자동 동기화를 가정하지 않는다.
- 잠금 표시는 협업 약속일 뿐 실제 파일 잠금이 아니다. 강제 잠금·원자적 수정 기능이 없다.
- 같은 작업 디렉터리에서 다른 세션의 파일·브랜치·미커밋 변경을 되돌리지 않는다.
- 비밀값, 실제 개인정보, 인증 토큰은 기록하지 않는다. 로그는 필요한 범위만 마스킹한다.
- 코드 줄 번호만이 아니라 커밋과 파일 경로를 함께 기록한다.
- 미실행·차단을 통과로 보고하지 않는다. Mock 통과와 실제 API 통과를 구분한다.

## 4. 상태·우선순위
작업 상태:
제안 → 승인대기 → 준비 → 진행 → 구현완료 → 검증대기 → 검증중 → 완료
예외 상태: 차단 / 재작업 / 취소

- 준비: 요구·수용 기준·담당·선행 조건이 합의됨.
- 구현완료: 담당자의 자체 검사 완료. 통합 검증 통과는 아님.
- 검증대기: 수정 커밋과 재현·자체 검사 증거를 인계함.
- 완료: 합의한 수용 기준을 지정 환경에서 검증하고 증거를 남김.
- 검증 실패는 재작업으로 돌리고 회차별 결과를 보존함.
- 테스트 판정은 작업 상태와 별도: 통과 / 실패 / 차단 / 미실행 / 해당 없음.
- 우선순위 P0: 격리·보안·데이터 손실 위험, P1: 핵심 흐름 차단, P2: 일반 기능 문제, P3: 개선.
- 심각도와 처리 우선순위는 같지 않을 수 있다. 우선순위 최종 결정은 조정자.
