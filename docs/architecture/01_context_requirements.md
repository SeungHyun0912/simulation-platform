# 01. 프로젝트 배경·요구사항

## 1. 목표와 비목표

목표: 다른 공장·사업체에도 적용할 수 있는 프로젝트 기반 생산 이산 시뮬레이션 플랫폼.
사용자는 공정·설비·공간·생산 시나리오를 등록하고 시뮬레이션 결과를 조회한다.
위키와 LLM은 동일한 기준정보와 실행 결과를 근거로 설명한다.
CAD는 위치·경로 편집을 돕는 입력 수단이며 엔진의 필수 의존성이 아니다.

초기 비목표:
- 실시간 설비 제어, PLC 명령 전송, 생산 자동 실행
- 3D 물리 엔진, 케이블의 상세 기계적 변형, 로봇 충돌 회피 제어
- 모든 제조 유형을 코드 추가 없이 처리하는 무제한 노코드 엔진
- CAD의 모든 객체를 PostgreSQL 행으로 적재
- LLM의 자율 변경·자율 실행·원시 SQL
- 프로젝트 간 실시간 공유 자원 스케줄링

## 2. 범위와 소유권

organization: 고객 사업체와 보안 경계.
project: 사용자가 선택하는 모델/실험 범위. 공장 전체나 일부 라인을 표현.
project_group: 프로젝트 안의 논리 그룹/라인. 여러 그룹이 동일 자산을 참조 가능.
zone: 배치 버전 안의 물리적 구역. 논리 그룹과 다르다.
asset: 설비/저장공간/도킹 지점의 고정 정체성.
asset_revision: 자산 능력·용량·정책의 버전.
node: 자산 IN/OUT/ACCESS 포트 또는 공정 그래프 노드. 두 용어를 DB 이름으로 구분.

프로젝트 복사 시 내부 ID를 새로 만들고 모든 참조를 변환한다.
다른 프로젝트의 같은 EQ 코드가 같은 실물 자원을 뜻하지 않는다.
동일 실행에서 공유 설비를 표현하려면 같은 프로젝트의 동일 asset_id를 사용한다.
복수 프로젝트 연합 실행은 별도 기능으로 유보한다.

## 4. 중요한 업무 용어

- 공정 단계: 제품 경로상의 방문. 같은 설비를 재방문해도 단계 ID는 다르다.
- 설비군: 한 역할을 수행할 후보 자산 집합. 하나 선택과 동시 확보를 구분.
- 작업(operation): 투입 구성 한 번을 확보하고 목표 산출을 만드는 실행 단위.
- 산출 단위(output unit): 다음 공정에 전달 가능한 보빈/롤/다발 하나.
- 보빈: 작업물의 포장·권취 형태. 보빈 개수는 전선 길이/가닥 수가 아니다.
- 가닥 수: 동시 공급 구성. 13가닥을 합친다고 13배 산출 길이가 되지 않는다.
- 잔량: 작업 후 남은 길이/중량. 설정에 따라 이월/폐기/보관.
- 가용: 설비 운전·점유·예약·근무시간 등을 만족하는 조건. 단순 idle만을 뜻하지 않음.
- 수용 가능: 목적지 용량과 필요한 자원·예약 조건을 만족.
- 생산 완료: 제품별 지정 공정 도달. 검사 완료·출하/적재와 다를 수 있다.

## 5. 단위 정책 — 설계 제안

저장/계산: 길이 m, 중량 kg, 시간 min, 좌표 m, 회전 degree.
서버 실제 시간: UTC timestamptz, 화면 Asia/Seoul 기본.
시뮬레이션 시각: 실제 날짜가 아니라 시작점 기준 min; 필요하면 시나리오 시작 일시에 매핑.
화면은 t/시간/초도 허용하되 변환값과 원입력 단위를 보존.
기준 수량은 numeric, API는 decimal string 사용. 엔진 시간은 검증 후 float 변환.
도면 좌표 단위와 모델 내 공정 길이 단위를 섞지 않는다.

## 6. 운영 가정 관리

미정 데이터가 있어도 초안 저장·위키 표시·설계 검토는 가능하다.
실행은 해당 시나리오가 사용하는 필수 정보만 검증한다.
임시값은 `scenario_version.assumptions`에 이유·승인자·대상 경로를 기록한다.
예: “이번 단일 공정 시험에서는 운반시간 0분 가정”은 허용 가능하나
“공장 전체 운반시간은 0분으로 확정”은 금지.

## 7. 초기 사용자 역할 — 제안

org_admin: 조직 관리 및 멤버 관리. 모든 프로젝트 열람은 별도 정책으로 명시.
project_admin: 프로젝트 설정·권한·보관 관리.
editor: 초안 수정, 검증 요청.
reviewer: 버전 승인/반려.
operator: 승인 모델 시나리오 실행/취소.
viewer: 승인 정보·허용된 결과 조회.
MVP에서는 계정 하나가 여러 역할을 가질 수 있으나 역할별 테스트는 분리한다.
