## 1. 원칙(기존 규칙 유지)
- 모르는 값은 unknown이고 0·무제한·해당 없음과 다르다. 부족한 값은 **시나리오 가정으로만** 채우고 공정 원본(master)에는 넣지 않으며, 실행 결과마다 쓴 가정을 보고한다.
- LLM이 만든 값도 같은 가정이다: 제안(`source=llm_proposed`)으로 저장되고 **사람이 승인한 뒤에만** 실행에 쓴다. 승인 전에는 실행에 영향이 없다.
- 설비·공정 이름·코드를 엔진 분기에 쓰지 않는다. 값은 공정 데이터와 시나리오 데이터로만 정한다.

## 4. 정리 중 발견한 영향(분석, 결정 필요)
- **a. 길이 없는 원자재(I-2):** 엔진의 도착(`Arrival.length_m`)과 작업물(`WorkItem.length_m`)은 길이가 필수다. 길이 없는 작업물(중량·개수만)을 받고, 첫 단계가 산출 길이를 정하는 구조가 필요하다. 길이로 시간을 재는 handler가 길이 없는 입력을 받으면 0으로 계산하지 않고 컴파일에서 막는다(해당 없음 ≠ 0). 공정 버전의 원자재 단위 길이는 `not_applicable`로 바꾼다(draft 6건이라 수정 가능, 시드 갱신).
- **b. P05 24개 vs 동시 11개(결정 I-6):** 작업 한 번에 11개를 한꺼번에 확보하므로 24개 입고면 2회(22개) 처리 후 **2개가 남는다**. 사용자는 24개를 유지하기로 했다. 문서 §13대로 남은 재고를 자동 폐기하거나 새 원자재를 만들지 않고, 엔진이 "남은 작업물이 모두 한 작업의 필요 수량(batch)을 못 채워 기다리는 중"임을 진단해 `stalled`의 사유를 `INSUFFICIENT_INPUT`으로 표시하고 남은 작업물과 부족한 수를 결과에 싣는다(현재는 `WIP_REMAINING` 하나뿐).
- **c. 멀티신선의 시간 기준(P04·P05):** 중간 반제품 기준(예: P04 40,000m 보빈 12개)으로 계산하되, 12개 보빈을 **동시(스트림별)** 로 만드는지 **순차** 로 만드는지가 아직 정해지지 않았다(설계 문서 예: 동시면 보빈당 400분, 순차면 전체 4,800분). 엔진은 둘 중 하나를 자동 선택하지 않는다.

## 6. 묶음별 결정 기록
### ① 후보 설비 자격 — 결정됨(2026-10-27 사용자)
- **제외할 설비 없음:** 문서의 후보 범위(실리콘 편조 EQ-003~010, 실리콘 테이핑 EQ-011~012, AL 더블 EQ-090~093, 절연 EQ-032~033, 재권취 EQ-085~088, CU 연선 EQ-015~020, CU 편조 EQ-039~080, CU 테이핑 EQ-081~084, 쉬스 압출기 EQ-034~035)는 모두 해당 단계를 할 수 있는 설비로 **확정**한다(`eligibility_status = confirmed`). 1대로 정해진 단계는 이미 확정이다.
- **설비 공유는 정상:** EQ-034~035는 P06에서 절연과 쉬스를, P05에서 쉬스를 맡고 한 호기가 번갈아 하는 것이 정상이다. 공정 정보가 다르면 사용자가 공정을 고쳐 다시 실행한다. EQ-036(보빈용 조사기 1대, 다발용 2대는 현재 6종 경로에 없음)은 P04·P05·P06이 몰리면 **병목이 되는 것이 정상**이다 — 결과 해석에 쓸 사실이며 오류가 아니다.
- **반영 방법:** 확정값이므로 **공정 데이터(draft)** 의 후보 `eligibility_status`를 바꾼다(가정이 아님). 6묶음 정리가 끝난 뒤 한 번에 시드를 갱신한다(draft 6건). 승인 때 후보 설비 번호가 고정되어 설비가 늘어도 자동 후보가 되지 않는다.

### ② 여러 후보 설비 중 선택 규칙 — 제안(동순위 선택 순서 확인 대기)
- **사용자 제안(2026-10-27):** 같은 설비가 여러 대면 동시에 생산할 수 있다. **가동 중이 아닌 설비부터 순서대로 시작**하고, **가동 중이 아닌 설비가 없으면 전체가 기다린다.**
- **엔진은 이미 이렇게 동작한다**(`simulation/resources/allocator.py`, 시험으로 순서 고정): 후보 목록 순서에서 비어 있는 첫 설비를 배정하고, 모두 가동 중이면 요청 순서(FIFO)로 기다리다 설비가 풀리면 가장 오래 기다린 요청이 받는다. 같은 설비를 쓰는 다른 단계·다른 제품도 한 줄로 기다린다(공유 설비). 컴파일은 후보가 둘 이상일 때 선택 규칙이 `fifo` 또는 `first_available`일 것을 요구하는데(현재 값이 `unknown`이라 막힘), **두 값이 엔진에서는 같은 동작**이다.
- **공정 데이터 값:** `allocation_rule = first_available`(사용자 설명과 같은 이름).
- **확인할 것(동순위):** "비어 있는 설비 순서"를 **설비 코드 순서**(EQ-003 → EQ-004 → …)로 하면 번호가 앞선 설비가 더 많이 쓰이고 뒤 설비는 덜 쓰인다(가동률이 한쪽으로 쏠림). 번호가 앞선 설비부터 채우는 것이 맞는지, 아니면 가장 오래 쉰 설비부터(돌려쓰기)인지 정해야 한다. 코드 순서는 현재 동작이고, 돌려쓰기는 작은 엔진 변경이 필요하다.
