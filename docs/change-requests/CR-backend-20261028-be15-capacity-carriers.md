# CR-backend-20261028-be15-capacity-carriers
- 요청자: Backend / 작업 BE-15(임시 ID) / 대상: contracts/04 §5.1(시나리오 가정)·§5.5(병목 한계), 07 §7·§8(blocking·이동)
- 상태: **사용자 결정 반영**(2026-10-28): "2번 운반자원을 모델에 넣는 작업과 3번 바로 진행하자", 공간 용량 22개 값 확정("맞음"), 운반 규칙 답변.
- 선행: 계약 0.14.0(PR #58 머지).

## 1. 사용자 결정
1. **공간 용량(동시 적재 개수):** ST-001 150, ST-002 20, ST-003 1, ST-004 16, ST-005 48, ST-006 96, ST-007 204, ST-008 56, ST-009 48, ST-010 25, ST-011 90, ST-012 139, ST-013 108, ST-014 30, ST-015 40, ST-016 40, ST-017 24, ST-018 38, ST-019 120, ST-020 9, ST-021 1, ST-022 1.
2. **운반 자원:** 지게차 3대는 지게차 운반 경로들이, AMR 2대는 AMR 운반 경로들이 함께 쓴다. 한 번에 1제품(이동 3분 + 상하차 1분).
3. **운반 뒤:** 꼭 돌아오지 않는다. 다음 명령이 없으면 목적지에서 기다린다.
4. **그 밖의 공간 사이 이동:** 사람이 옮기며 시간은 고려하지 않는다(지금 그대로).

## 2. 구현(계약 0.15.0, 추가만, migration 없음)
- **운반 자원 = 설비 자원:** 지게차·AMR을 설비 자산(FL-001~003, AMR-001~002)으로 만들고 운반 단계(`transport_manual`)의 후보 설비로 둔다(선택 규칙 first_available). 같은 자산이 여러 운반 단계·제품의 후보라 대수가 공유된다(기존 설비 배정기 그대로).
- **위치 추적(엔진):** 운반 자원이 운반을 마치면 목적지에 머문다. 다른 곳에서 일을 받으면 그곳까지 빈 차로 이동한 뒤 운반한다(이벤트 `CARRIER_MOVED`, 이동 중 설비 상태는 RESERVED). 처음 쓰는 자원은 그 자리에 있다고 본다(초기 위치 모름).
- **빈 차 이동 시간은 시나리오 가정** `carrier_empty_move_minutes`(분, 0 허용): 공간 사이 거리는 정보가 없어(네트워크 정보는 쓰지 않음) 사용자가 준 "이동 3분"을 시연 시나리오의 가정으로 쓴다. 운반 단계에 설비 후보가 있는데 이 값이 없으면 컴파일 오류 `CARRIER_EMPTY_MOVE_UNKNOWN`.
- **출력 대기 가정** `out_release: hold`: 다음 공간이 유한해 막힐 수 있으면 설비마다 OUT 배출 정책(DEC-006)이 필요한데 승인된 설비 자산 버전이 없다. 시나리오가 "가득 차면 산출을 쥐고 기다린다"를 명시하면 정책이 없는 설비에만 적용한다(정책이 있는 설비는 그 정책). 가정 코드 `OUT_RELEASE_HOLD`.
- **가정 코드 분리:** 공간 용량이 미정인 곳(`UNBOUNDED_BUFFERS`)과 단계 사이 직접 인계(`UNBOUNDED_HANDOFFS`)를 따로 보고한다(둘 다 `unbounded_buffers`로 허용). 병목 요약의 "공간 부족 평가 불가" 한계는 앞의 것만 따른다.
- **병목 요약 한계 문구:** 운반 자원을 모델링한 실행이면 "지정된 대수와 위치로 계산"으로 바뀐다.
- **사전검증:** 새 가정 두 개도 "가정을 쓰면 사유 필요"(SCN-ASM-001)에 포함.

## 3. 범위 밖
- 공간 사이 거리·경로(네트워크)와 운반 자원의 경로 충돌, 배터리·충전, 운반 자원의 작업 우선순위(지금은 요청 순 FIFO, 비는 자원 중 코드 순).
- 원자재 입고 위치(source 노드, ST-001·005·017)의 용량은 엔진이 아직 적용하지 않는다(입고는 그대로 들어온다).
