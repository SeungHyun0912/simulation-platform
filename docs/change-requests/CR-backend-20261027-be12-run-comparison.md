# CR-backend-20261027-be12-run-comparison
- 요청자: Backend / 작업 BE-12(임시 ID, 결과 분석 API 3종 중 셋째) / 대상: contracts/04 §5(비교 행), 07 §10
- 상태: **사용자 지시로 진행**("후보로 정해준 API들을 순서대로 개발해 줘", 2026-10-27 — 셋째 후보 "비교 API"). API 담당이 권장안 승인으로 해석, 정정 가능.
- 선행: CR be10(0.12.0), CR be11(타임라인). **계약 0.13.0에 be11과 함께 묶어 승격한다**(0.12.0이 main에 게시된 뒤).

## 1. 왜 필요한가
"설비 한 대를 늘리면/입고를 바꾸면 무엇이 달라지나"를 보려면 두 실행의 입력 차이와 결과 차이를 한 화면에 놓아야 한다. 지금은 UI가 두 run의 지표를 각각 받아 맞춰야 하고, 공정 버전이 바뀌면 지표 차원(공정 버전 id)이 달라 맞출 수도 없다.

## 2. 04 초안과 다른 점(제안)
04 §5 표의 `POST /comparisons`·`GET /comparisons/{id}`(비교를 저장)는 두지 않고, **저장 없이 두 run을 바로 비교하는 조회**로 시작한다. 실행 결과·입력 스냅샷이 불변이라 같은 두 run의 비교 결과도 늘 같으므로 저장할 이유가 적다. 비교에 이름·메모를 붙여 공유할 필요가 생기면 저장형을 추가한다.

## 3. 범위(계약 0.13.0, 추가만, migration 없음)
1. `GET /projects/{p}/runs/{r}/compare/{other}`(viewer): 비교 요약.
   - `comparable`·`warnings`: 엔진 버전이 다름, 한쪽에만 있는 제품(그 제품은 비교 대상에서 빠짐), 결과가 complete가 아님(관측 중단·미완료), 종료 규칙이 다름(관측 기간이 다름) 등을 알린다. 엔진 버전이 다르면 `comparable=false`.
   - `input_changes[]`: 입력 스냅샷 차이 — seed·replicate_index·엔진 버전·이벤트 한도·종료 규칙·시나리오 버전·가정 사유, 제품별(제품 id 기준) 추가/삭제·공정 버전·도착·가정·처리 순서, 고정 자산의 엔진 입력(용량·배출 규칙). 공정 그래프 내용의 차이는 기존 `GET /process-versions/{v}/diff?against=`로 본다(여기서는 버전 id만).
   - `products[]`: 제품별 핵심 결과 나란히(완료 수·길이, 처리량, 리드타임 평균, 끝 재공품, 마지막 완료 시각)와 차이.
   - `end_time`(두 run의 관측 종료 시각), `bottlenecks`(양쪽 상위 5개).
2. `GET /projects/{p}/runs/{r}/compare/{other}/metrics?metric_key&window=run&changed_only&limit&cursor`(viewer): 지표 차이 행 — 같은 지표·차원·구간의 기준값·비교값·차이(비교 − 기준)·비율(비교 ÷ 기준, 기준이 0·null이면 null). **공정 버전이 달라도 같은 제품이면 맞춘다**(차원의 `process_version_id`를 제품으로 바꿔 맞추고 양쪽 공정 버전 id를 함께 준다). 한쪽에만 있는 행은 다른 쪽 값이 null이다.
- 두 run은 같은 프로젝트여야 하고(다르면 404) 둘 다 공식 결과가 있어야 한다(없으면 409 `RUN_RESULT_NOT_AVAILABLE`). 같은 run끼리 비교는 422.

## 4. 원칙
- 비교는 저장된 입력 스냅샷과 지표만 쓴다(재계산 없음). 수치는 decimal 문자열.
- 여러 제품의 생산량을 합산한 비교 값은 만들지 않는다(07 §10).
- 결과가 확률 요소 없이 결정적이라(같은 입력이면 같은 결과) 차이는 입력 차이에서 온다. 반복 실행 통계(신뢰구간)는 확률 요소가 생긴 뒤의 일이다.
