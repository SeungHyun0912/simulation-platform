# CR-backend-20261027-be13-batch-process-graphs (후보)
- 요청자: Frontend(FE 세션 제안, 2026-10-27) / 기록: Backend / 대상: contracts/04 §4(공정 버전·그래프 API)
- 상태: **사용자 승인·구현**("시나리오를 최신 승인 공정으로 갱신 하는 기능 개발과 공정 일괄 조회 기능 같이 개발해 줘", 2026-10-27). 구현 범위는 CR be14 §4(계약 0.14.0). 처음에는 FE 제안의 후보로 기록했다.

## 1. 배경
FE가 프로젝트의 모든 제품 공정을 한 화면에 그리는 화면(여러 제품이 함께 쓰는 설비 강조)을 만들었다. 지금은 제품마다 `GET /process-versions/{v}/graph`를 동시 6개까지 보낸다. DEMO-WIRE 6종은 문제없으나 제품이 수십~수백 종이면 요청 수가 많아진다.

## 2. 제안(FE 안)
1. `GET /projects/{p}/process-graphs?version_ids=…`(또는 `basis=latest|approved`): 여러 공정 버전의 `GraphOut`(또는 노드·간선 요약)과 버전별 ETag(row_version)를 한 번에. 권한·프로젝트 범위는 지금과 같다.
2. 선택: 설비별 사용처(어느 제품의 어느 단계가 그 설비를 후보로 쓰는지)를 서버가 계산.

## 3. Backend 의견(결정 전 참고)
- 실행 결과 쪽에는 이미 설비별 사용처가 있다: 0.13.0 `GET /runs/{r}/asset-timeline`의 `uses[]`(그 실행의 입력 스냅샷 기준). 기준정보(현재 공정) 쪽 사용처는 없다.
- 일괄 조회는 추가만이라 호환된다. 응답 크기 때문에 `version_ids` 개수 상한(예: 50)과 노드·간선 요약 모드(단계 상세 제외)를 함께 두는 것을 권장한다.
- 설비별 사용처는 `GET /projects/{p}/assets/{asset_id}/uses?basis=latest|approved` 같은 별도 조회가 단순하다.

## 4. 결정이 필요한 것
- 언제 할지(제품 수가 늘어나는 시점), 요약 모드 범위, 사용처를 일괄 조회에 넣을지 별도로 둘지.
