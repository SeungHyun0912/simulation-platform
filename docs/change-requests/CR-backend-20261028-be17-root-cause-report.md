# CR-backend-20261028-be17-root-cause-report
- 요청자: Backend / 작업 BE-18(임시 ID) / 대상: contracts/04 §5.5(병목 요약), §5(실행 결과)
- 상태: **사용자 승인**("리포트 묶음 API를 포함해서 원인 추적 기능을 개발해줘", 2026-10-28). LLM 없이 규칙으로 계산한다(사용자 질문에 대한 답변으로 확인).
- 선행: 계약 0.15.2(PR #61 머지).

## 1. 왜 필요한가
병목 요약은 "멈춘 곳"을 순위로 보여 주므로 하류 설비가 느리면 막힘이 상류로 번져 상류가 1위가 된다(실제 6공정: P04 AL 더블 집합 출력 막힘 1위, 근본은 싱글 메인 EQ-096). 사용자는 결과와 병목 원인을 한 번에 받아 보고서로 보고 싶어 한다.

## 2. 원인 추적(규칙, 결정적)
막힌 곳에서 하류로 따라간다.
- **단계**가 출력이 막혀 있으면(출력 막힘 ≥ 60작업물·분) 다음 위치로 간다(다음이 공간이면 그 공간, 직접 인계면 다음 단계).
- **공간**이면 그 공간에서 꺼내 가는 단계들 중 더 많이 막힌 단계(막힘이 없으면 처리 시간이 긴 단계)로 간다.
- 막히지 않은 단계에 닿으면 그 단계가 **근본 원인**이다(후보 설비의 가동률을 근거로 단다).
- 시작 위치: 출력 막힘 → 그 단계, 공간 대기 → 그 공간, 적체 → 그 공간, 설비 대기 → 그 단계(그 단계가 막혀 있지 않으면 자기 자신이 원인).
- 같은 곳을 다시 지나거나 20단계를 넘으면 멈추고 원인을 "판정 불가"로 둔다.

## 3. API(계약 0.16.0, 추가만)
- `GET /runs/{r}/bottlenecks`: 후보마다 `root_cause`(공정 버전·제품·단계·후보 설비와 가동률·설명, 판정 불가면 null)와 `chain`(막힘이 번진 경로: 단계·공간 목록). 요약에 `root_causes[]`(근본 원인별로 묶은 후보 수와 멈춘 양, 순위)와 headline에 근본 원인 문장.
- `GET /runs/{r}/report`(viewer): 결과 리포트 묶음 — 실행(상태·종료 사유·관측 기간·엔진 버전·품질), 시나리오(코드·버전·종료 규칙·가정 사유), 사용한 가정, 제품별 핵심 지표(완료·처리량·리드타임·재공품·폐기·마지막 완료·입력 부족), 병목(요약·근본 원인), 설비 가동률 상위·대기 공간 적체 상위, 한국어 요약 문장(규칙으로 생성), 한계. 공식 결과가 없으면 409 `RUN_RESULT_NOT_AVAILABLE`.

## 4. 원칙
- 모든 수치는 저장된 지표·스냅샷에서 온다(재실행·LLM 없음). 같은 run이면 같은 리포트.
- 서로 다른 제품의 생산량을 합산하지 않는다.
